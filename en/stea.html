Case study · flagship project

STEA, from idea to production

How I designed, built and deployed, end to end, a logistics and stock management application now used by STEA Trans Euro Afrika SARL, in Lomé.

My role
Design, development, deployment and maintenance

01 · The challenge

Knowing at any moment what is in stock, where, and what to reorder

STEA Trans Euro Afrika runs several warehouses, buys from suppliers, delivers to customers and handles returns. Without a central tool, that kind of information scatters across files and notebooks: the real state of the stock becomes uncertain, shortages are discovered too late and nobody can tell who did what.

The application therefore had to keep a reliable, multi-warehouse stock, cover the whole purchase → delivery → return cycle with its documents, raise alerts automatically before a shortage, separate roles with precise rights and stay simple to install on the company Windows machines, with no on-site technical work at every update.

Stock you can trust

Several warehouses, batches and serial numbers, stock counts and traced resets: every quantity displayed has to match reality.

The full cycle

Supplier purchase orders, deliveries, delivery notes, returns and credit notes, payments received: the documents follow on from each other without re-typing.

Precise rights

A stock operator, a logistics manager, an accountant and a sales agent do not see the same thing and cannot perform the same actions.

02 · My answer

A solid API, a clear interface, a one-click install

I separated the responsibilities clearly: a Spring Boot server that carries all the business rules and the security, a React interface that only presents and guides, and an Electron desktop application that embeds that interface and updates itself. The same interface is also served as a web version by the server: one codebase, two channels.

Desktop application

Electron + React 18, Tailwind CSS, Recharts. Windows installer, automatic update at launch through GitHub Releases (electron-updater). The server address is read from a remote configuration file: changing server requires no new release.

HTTPS · JSON

Server

Spring Boot 3 / Java 17, a REST API of 173 endpoints, 31 JPA entities on MySQL. JWT authentication, role-based authorisation on every endpoint, activity audit log.

Operations: a self-hosted, supervised server (database, server and tunnel restarted automatically after an outage), exposed to the internet through a secure tunnel with a fixed address, with a backup of the database and of the previous release before every deployment.

03 · Security and quality

The screen hides, the server forbids

Every access rule exists twice: once in the interface, to show only what is allowed, and once in the server, which refuses what is not, whatever the client sends. Eight roles share the application, including three read-only agent profiles limited to the items of their own department.

Access

  • JWT token authentication (Spring Security)
  • Rate limiting on sign-in attempts
  • Authorisation checked endpoint by endpoint

Traceability

  • Audit log: who did what, and when
  • Stock and payment resets are traced
  • Database backup before every deployment

Verification

  • 141 automated tests on the server side
  • Every change tried on an isolated instance with a throwaway database before going live
  • A written, repeatable deployment procedure

04 · Results

In production, and still evolving

The first desktop release was published on 12 August 2026. Since then the application has evolved at the pace of the company’s needs: 29 releases delivered by automatic update in five weeks, without ever reinstalling a machine.

One example of a change requested by the company: three read-only agent profiles, each limited to the items of their own department. Mock-up proposed in the morning, approved the same day, server updated that same day.

05 · What I learned

Three lessons I keep

  1. Shipping is more than coding

    A running server cannot be swapped in place: stop, back up, replace, restart, in that order. I learned it by breaking the server once, and turned it into a written procedure I follow at every deployment.

  2. The server decides, the screen suggests

    Hiding a button protects nothing. Every access rule is checked on the server, and the interface only reflects what is allowed.

  3. Check before announcing

    Before saying “it is live”, I replay the feature on an isolated instance with a throwaway database. A demonstration beats a promise.
