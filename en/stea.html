Case study · flagship project

STEA, from idea to production

How I designed, built and deployed, end to end, a logistics and stock management application now used by STEA, in Lomé.

Client
STEA · Lomé, Togo
My role
Design, development, deployment and maintenance
Period
July – September 2026 · in production since August 2026
Technologies
Java 17 · Spring Boot · MySQL · React · Tailwind CSS · Electron

01 · The challenge

Knowing at any moment what is in stock, where, and what to reorder

STEA runs several warehouses, buys, delivers and handles returns. Without a central tool, that kind of information scatters: the real state of the stock becomes uncertain and shortages are discovered too late.

The application therefore had to keep a reliable stock across several warehouses, cover the whole purchase → delivery → return cycle, raise alerts before a shortage and stay simple to install on the company machines.

Stock you can trust

Several warehouses, batches and serial numbers: every quantity displayed has to match reality.

The full cycle

Orders, deliveries, returns: the documents follow on from each other without re-typing.

Precise rights

Each role sees what concerns it and acts only within its own scope.

02 · My answer

A solid API, a clear interface, a one-click install

I separated the responsibilities clearly: a server that carries the business rules and the security, an interface that presents and guides, and a desktop application that embeds that interface and updates itself.

Desktop application

Electron and React: a Windows installer, and updates arrive on their own at launch.

HTTPS · JSON

Server

Spring Boot and MySQL: a REST API carrying the business rules, the authentication and the role-based rights.

03 · Security and quality

The screen hides, the server forbids

Every access rule exists twice: in the interface, to show only what is allowed, and in the server, which refuses the rest. Several roles share the application, some of them read-only.

Access

  • Every account has a role, and every role a scope
  • Rights are checked on the server, not only on screen

Traceability

  • An audit log keeps who did what, and when
  • Sensitive operations are traced

Verification

  • An automated test suite on the server side
  • Every change is tried on a test instance before going live

04 · Results

In production, and still evolving

The first version went into service in August 2026. Since then every change has arrived by automatic update, without ever reinstalling a machine.

One example of a change requested along the way: new read-only profiles. Mock-up in the morning, approved the same day, delivered that day.

05 · What I learned

Three lessons I keep

  1. Shipping is more than coding

    Updating a tool people use every day takes method. I wrote my procedure down and follow it every time, rather than improvising.

  2. The server decides, the screen suggests

    Hiding a button protects nothing: rights are checked on the server, and the interface only reflects what is allowed.

  3. Check before announcing

    Before saying “it is live”, I replay the feature on a test instance. A demonstration beats a promise.
